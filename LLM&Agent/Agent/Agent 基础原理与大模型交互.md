# Agent 核心概念详解

## 一、大模型 API 是什么？

一句话：**API 是你的程序与大模型进行通信的接口。**

假设你要开发一个电价分析 Agent，需要大模型帮你理解用户的问题。Python 程序本身并不能直接获得大模型的推理能力，就需要通过 API 向模型发送请求。

```
你的 Python 程序
    ↓
用户提出："分析昨天的电价预测效果"
    ↓
大模型 API
    ↓
发送请求、传递参数、接收响应
    ↓
大模型
    ↓
理解问题，生成分析思路或工具调用请求
```

### 一次典型的 API 调用包括：

1. 你的程序发送输入消息、模型名称等参数
2. API 服务将请求交给对应的大模型
3. 模型生成结果
4. API 将结果返回给你的程序
5. 程序继续处理结果，或者把结果展示给用户

例如，使用 Python 调用模型，逻辑大致如下：

```python
response = model.invoke("什么是日前电价？")
print(response.content)
```

这里的 `model` 是提前配置好的模型调用对象。

### 你必须理解的几个细节

- **API Key**：用于身份认证和授权，类似访问凭证，不能泄露
- **模型名称**：决定请求使用哪个模型
- **请求参数**：包括消息、输出长度限制等
- **响应结果**：可能是普通文本，也可能是结构化数据或工具调用请求
- **异常处理**：可能出现网络超时、限流、认证失败等问题

> ⚠️ **注意**：API 不等于大模型本身。它是你的程序访问模型服务的一种方式。

## 二、Prompt 是什么？

一句话：**Prompt 是你提供给大模型的指令和上下文，用来告诉模型应该做什么、依据什么做、按什么格式输出。**

比如，你直接问模型：

> 分析一下电价。

这个问题过于模糊。模型不知道你要分析日前电价、实时电价，还是预测误差。

你可以把 Prompt 写得更明确：

```
你是一名电价预测分析助手。

任务：
分析用户提供的日前电价预测结果。

要求：
1. 计算预测值与实际值的误差。
2. 找出误差最大的时段。
3. 给出简洁的分析结论。
4. 不允许编造数据。
5. 如果缺少实际电价数据，明确说明无法计算误差。
```

这样模型就更清楚自己的任务和限制。

### Prompt 通常包含什么？

| 组成部分 | 说明 |
|---------|------|
| **角色与任务** | 告诉模型它负责什么，例如电价分析助手 |
| **上下文与数据** | 提供用户问题、历史对话、业务数据或检索到的知识 |
| **规则与约束** | 说明允许做什么、不能做什么、什么情况下需要追问或调用工具 |
| **输出要求** | 要求返回普通文本、JSON 或指定的数据结构 |

### Prompt 有什么局限？

Prompt 可以引导模型，但不等于程序级的强制约束。

例如，你在 Prompt 中写"绝对不能输出错误的 JSON"，模型仍然可能输出格式不合法的内容。

因此，工业级开发中通常还需要：

- 使用结构化输出机制
- 使用 Pydantic 等工具校验数据
- 对重要业务规则在代码中进行二次检查
- 对模型没有依据的内容进行限制

> 💡 **记住**：Prompt 负责引导模型，代码负责执行强约束。

## 三、Token 和上下文窗口是什么？

这两个概念很容易混淆。

### 1. Token 是什么？

Token 是大模型处理文本时使用的基本单位。

它不完全等于一个汉字、一个单词或一个字符。不同的文字、符号和模型分词方式，产生的 Token 数量可能不同。

例如：

> 请分析昨天的电价预测效果。

这句话会被模型切分成若干 Token，再转换为模型能够处理的数字表示。

#### 为什么要关注 Token？

- API 通常会根据输入和输出 Token 数量计算费用，具体取决于服务商和模型
- Token 数量会影响处理速度
- 输入太长可能超过模型的上下文限制

### 2. 上下文窗口是什么？

上下文窗口是模型单次处理时能够容纳的上下文总量上限。

可以把它理解成模型当前这次任务的工作空间。

假设某个模型的上下文窗口是 32,000 Token，那么系统需要在这个容量范围内安排输入和输出。具体计费与容量规则以所用模型为准。

#### 上下文窗口示意图（非实际比例）

```
┌─────────────────────────────────────────┐
│  系统 Prompt                             │
├─────────────────────────────────────────┤
│  用户问题与历史对话                       │
├─────────────────────────────────────────┤
│  检索内容、工具调用结果                   │
├─────────────────────────────────────────┤
│  模型生成的输出                           │
└─────────────────────────────────────────┘
```

这些内容会共同占用模型可用的上下文容量，具体计算规则因模型而异。

### 为什么工业级 Agent 特别需要关注上下文？

假设你开发的 Agent 与用户进行了 100 轮对话。

如果每次都把全部历史记录发送给模型，输入会越来越长，成本也可能不断上升，甚至超出上下文窗口。

因此需要考虑：

- 只保留最近的相关对话
- 将较早的对话压缩成摘要
- 将长期知识放到数据库，需要时再检索
- 将任务进度保存在独立的状态存储中

这里有个关键区别：

> 📌 **对话历史、长期记忆和任务状态不是同一个东西。** 你之前接触过 JSON/Markdown 和向量数据库，它们可以分别承担不同的存储职责，但向量数据库并不是所有记忆都必须使用的组件。

## 四、什么是结构化输出 JSON？

一句话：**结构化输出就是让模型按照预先定义的数据格式返回结果，而不是随意生成一段文字。**

假设你让模型识别用户的任务类型。

普通文本输出可能是：

> 用户想要分析昨天的实时电价预测效果，应该查询数据并计算误差。

这段话人能看懂，但程序不容易稳定地提取任务类型、是否调用工具等字段。

如果要求模型返回 JSON：

```json
{
  "task_type": "price_analysis",
  "need_tool": true,
  "reason": "需要查询数据并计算预测误差"
}
```

程序就可以读取这些字段，并决定下一步做什么。

### 为什么 Agent 需要结构化输出？

例如，你可以定义一个 Pydantic 模型：

```python
from pydantic import BaseModel

class TaskDecision(BaseModel):
    task_type: str
    need_tool: bool
    reason: str
```

这个模型定义了三个字段及其类型。

当模型返回结果后，程序可以进行结构校验：

```python
decision = TaskDecision.model_validate(data)
print(decision.task_type)
```

如果数据缺少必填字段，或字段类型不符合要求，校验就可能失败。

> ⚠️ **需要注意**：这里的 `data` 必须是已解析的 Python 字典等有效输入。真实项目中，你可以让模型集成直接返回经过校验的 Pydantic 对象，或者先解析 JSON 再验证。

### 结构化输出不等于结果一定正确

例如：

```json
{
  "task_type": "price_analysis",
  "need_tool": false,
  "reason": "无需查询任何数据"
}
```

这个 JSON 在格式上完全可能合法，但对于需要计算昨天预测误差的任务，判断可能是错的。

所以要区分三件事：

| 层面 | 检查什么 |
|------|---------|
| **格式正确** | 是否符合 JSON 格式 |
| **类型正确** | 字段类型、必填字段是否符合定义 |
| **业务正确** | 判断是否合理、数据是否真实、任务是否完成 |

> 💡 工业级 Agent 不仅要检查格式，还要检查业务结果。

## 五、Agent 和普通大模型对话有什么区别？

**这是今天最重要的一个概念。**

普通大模型对话主要是生成回答；Agent 则能够根据任务决定下一步行动，调用工具，并根据执行结果继续处理。

我们用同一个电价分析问题来比较。

### 普通大模型对话

1. 用户问：帮我分析昨天的实时电价预测效果。
2. 模型可能根据已有上下文解释分析方法，或者要求用户提供数据。
3. 但如果没有实际数据，也没有连接数据库的工具，它就不能凭空知道昨天的预测误差。

### Agent

1. **第 1 步：理解任务** → 需要分析实时电价预测效果
2. **第 2 步：选择工具** → 调用 Python 函数查询预测值和实际值
3. **第 3 步：执行计算** → 计算 MAE、RMSE，定位误差最大的时段
4. **第 4 步：整理结果** → 模型结合真实计算结果生成分析报告

这就是 Agent 的基本执行过程。

### Agent 的关键组成

| 组成 | 作用 |
|------|------|
| **大模型** | 理解任务、进行判断、决定下一步行动 |
| **Prompt** | 提供任务指令和行为约束 |
| **Tools** | 执行查询、计算、文件处理等实际操作 |
| **执行循环** | 将模型决策、工具执行和结果反馈连接起来 |
| **State / Memory** | 保存任务进度和需要继续使用的信息 |
| **Guardrails** | 限制权限、校验输入输出、控制风险 |

> ⚠️ **特别注意**：模型提出工具调用请求，并不代表工具已经执行。通常是你的 Python 程序接收请求、校验参数、执行工具，再将结果返回模型。

另外，并非每个 Agent 都需要复杂规划。很多业务任务用固定工作流更可靠；只有在需要动态选择下一步时，才有必要把更多决策交给模型。

## 六、把这五个概念串起来

假设你要开发一个电价预测分析 Agent，整个过程是这样的：

1. **用户输入问题** → "分析昨天的实时电价预测误差。"
2. **Prompt 约束任务** → 说明分析目标、可用工具和输出要求
3. **通过 API 调用模型** → 请求和响应消耗 Token，并受上下文窗口限制
4. **结构化输出** → 模型返回任务判断或工具调用请求，程序校验其格式与参数
5. **Agent 执行工具** → 查询真实数据、计算指标、将结果返回模型，最终输出报告

### 一句话总结

> **API 负责通信，Prompt 负责指令，Token 衡量文本处理单位，上下文窗口限制单次可处理的信息量，结构化输出让结果更容易被程序处理，Agent 则把模型的决策与真实工具执行连接起来。**
