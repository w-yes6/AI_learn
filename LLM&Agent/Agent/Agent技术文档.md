# Agent 技术文档

## 1. 概述

Agent（智能体）是一个以大语言模型（LLM）为核心，能够围绕目标理解任务、制定计划、调用工具、观察执行结果，并根据反馈继续行动的软件系统。

普通的 LLM 通常遵循“输入文本 → 输出文本”的模式；Agent 则遵循“目标 → 决策 → 行动 → 观察 → 再决策”的闭环。Agent 的能力不只来自模型本身，也来自工具、记忆、执行器和运行控制等工程组件。

可以用一句话概括：

> LLM 提供理解和决策能力，Agent 系统让这种能力能够持续、可控地作用于真实环境。

## 2. Agent 与普通 LLM 的区别

| 对比项 | 普通 LLM 应用 | Agent 系统 |
|---|---|---|
| 主要输入 | 一次或多轮文本 | 目标、上下文、环境状态 |
| 输出 | 文本、结构化结果 | 工具调用、状态变化、最终结果 |
| 执行方式 | 通常一次生成 | 多轮决策和执行 |
| 对外部世界的作用 | 有限，通常只给建议 | 可读写文件、查询数据库、调用 API 等 |
| 下一步如何确定 | 由用户继续提问 | 可根据工具结果自动决定 |
| 失败处理 | 需要用户重新描述 | 可重试、修正参数、重新规划或请求人工介入 |

仅仅给聊天机器人增加一个系统提示词，并不会自动变成 Agent。只有当系统具备目标导向的行动逻辑、工具执行和结果反馈机制时，才具有典型的 Agent 特征。

## 3. Agent 的核心组成

### 3.1 大语言模型（LLM）

LLM 是 Agent 的推理和决策核心，主要负责：

- 理解用户目标和约束；
- 提取任务所需的上下文；
- 判断需要哪些工具；
- 生成计划或下一步行动；
- 解释工具返回结果；
- 判断任务是否完成；
- 生成最终答复。

模型可以是同一个模型承担多种角色，也可以使用不同模型分别负责规划、执行和审查。后者可能降低成本或提高稳定性，但会增加系统复杂度。

### 3.2 规划模块（Planning）

Planning 负责回答两个问题：

1. 任务需要拆成哪些步骤？
2. 这些步骤的执行顺序和依赖关系是什么？

例如“分析 CSV 并生成报告”可以拆成：

1. 定位并读取文件；
2. 检查字段、类型、缺失值和重复值；
3. 计算统计指标并识别异常；
4. 生成图表和结论；
5. 输出报告。

Planning 不一定是独立模型。常见实现方式包括：

- **固定工作流**：由程序预先写好步骤，稳定、容易测试；
- **LLM 动态规划**：让模型根据任务生成结构化计划，灵活性高；
- **动态规划与重规划**：每执行一步就观察结果，再决定后续步骤，更适合结果不确定的任务；
- **混合规划**：关键步骤固定，局部步骤由模型动态决定。

### 3.3 工具（Tools）

工具负责执行模型无法直接完成或不应直接完成的操作，例如：

- Python 代码执行；
- 文件读写和解析；
- 数据库查询；
- 搜索和网页访问；
- HTTP/API 调用；
- 发送消息或创建任务；
- 绘图、计算和文档生成。

模型只负责提出工具调用请求，工具由程序在真实运行环境中执行，并返回结构化结果。模型说“运行 Python”不等于代码已经运行，只有执行器真正运行并返回结果，这一步才算完成。

一个工具通常应定义名称、用途、输入参数、参数类型、权限范围和返回格式。例如：

```json
{
  "name": "read_csv",
  "description": "读取 CSV 文件并返回字段和数据摘要",
  "parameters": {
    "type": "object",
    "properties": {
      "path": {"type": "string"}
    },
    "required": ["path"]
  }
}
```

### 3.4 记忆（Memory）

记忆用于保存能够帮助当前任务的信息，包括：

- 当前对话历史；
- 用户偏好；
- 项目配置；
- 已完成步骤和中间结果；
- 历史任务和经验；
- 外部知识和文档。

常见实现方式：

| 类型 | 存储内容 | 特点 |
|---|---|---|
| 短期记忆 | 当前对话和当前任务状态 | 直接放入上下文，速度快 |
| 文件记忆 | JSON、Markdown、日志 | 简单透明，便于人工查看 |
| 结构化存储 | MySQL、PostgreSQL、SQLite | 适合查询和事务管理 |
| 向量记忆 | Embedding + 向量数据库 | 适合按语义检索历史内容 |
| 外部知识库 | 文档、网页、企业数据 | 为模型提供领域知识 |

记忆不等于模型学习。保存一条历史记录不会修改模型参数；通常是先检索相关信息，再把它作为上下文提供给模型。

### 3.5 执行器（Executor）

执行器负责把模型生成的动作转换为真实操作，通常包括：

- 解析模型输出；
- 校验工具名称和参数；
- 检查权限和资源范围；
- 调用工具；
- 记录输入、输出和耗时；
- 将成功或失败结果返回模型。

执行器应当是确定性的。模型负责选择动作，程序负责以明确规则执行动作。

### 3.6 状态管理与安全控制

运行控制模块负责管理：

- 当前任务状态（待执行、执行中、成功、失败、暂停）；
- 最大循环次数和超时时间；
- 重试次数和退避策略；
- 工具调用权限；
- 文件、网络和数据访问范围；
- 高风险操作的人工确认；
- 审计日志和错误记录。

对于删除文件、修改生产数据、发送外部消息、执行高权限命令等操作，应设置明确的权限边界和确认机制。

## 4. Agent 的基本运行流程

典型流程如下：

```text
接收用户目标
    ↓
加载上下文和相关记忆
    ↓
模型理解任务并生成计划或下一步动作
    ↓
校验动作和权限
    ↓
执行工具
    ↓
观察工具结果
    ↓
判断是否完成
  ┌─┴──────────────┐
否                  是
│                   │
重新规划/继续执行    生成最终结果
```

以“计算 CSV 的 MAE”为例：

1. 用户提出计算需求；
2. 模型判断需要读取 CSV 和计算指标；
3. 执行器调用文件工具或 Python 工具；
4. 工具返回数据摘要和 MAE；
5. 模型判断是否还需要解释异常；
6. 输出数值、计算方法和必要说明。

关键点在于：工具结果会重新进入模型上下文，模型可以根据真实结果改变原计划。

## 5. Planning 的技术实现

### 5.1 结构化计划

最简单的方式是让模型返回 JSON，程序负责解析和执行：

```json
{
  "goal": "分析 CSV 并生成报告",
  "steps": [
    {
      "id": 1,
      "task": "读取 CSV 文件",
      "tool": "read_csv",
      "depends_on": []
    },
    {
      "id": 2,
      "task": "检查缺失值、重复值和异常值",
      "tool": "analyze_data",
      "depends_on": [1]
    },
    {
      "id": 3,
      "task": "生成分析报告",
      "tool": "generate_report",
      "depends_on": [2]
    }
  ]
}
```

程序需要检查：步骤 ID 是否唯一、工具是否存在、参数是否符合 schema、依赖步骤是否已经完成，以及计划是否超出权限范围。

### 5.2 重规划

计划不应被视为不可改变的脚本。执行结果可能导致：

- 文件不存在；
- 数据字段与预期不一致；
- 工具返回部分结果；
- 权限不足；
- 计算结果异常；
- 用户目标发生变化。

此时 Agent 可以选择重试、修改参数、增加补充步骤、询问用户或终止任务。重规划通常比机械执行预设步骤更可靠。

### 5.3 Planning 与模型思考的关系

Planning 是大模型能力的一种系统化使用方式，而不是一定独立存在的模型：

- **大模型**是负责理解、推理和决策的核心；
- **Planning**是将复杂目标拆成可执行步骤的功能；
- **Executor**是按规则执行步骤的程序；
- **反馈循环**将执行结果交给模型继续决策。

可以使用同一个模型分别调用“生成计划”和“根据结果决定下一步”两个 Prompt，也可以为规划、执行和审查配置不同模型。

## 6. 最小 Agent 架构

一个可用于学习和原型开发的最小架构包括：

```text
用户输入
  ↓
Agent Controller
  ├─ Context/Memory：组装上下文
  ├─ LLM：生成计划或工具调用
  ├─ Tool Router：校验并路由工具
  ├─ Executor：执行工具
  └─ State Store：保存状态和日志
```

伪代码如下：

```python
def run_agent(user_goal, max_steps=10):
    state = load_state(user_goal)
    context = build_context(user_goal, state)

    for _ in range(max_steps):
        decision = llm_decide(context, available_tools())

        if decision["type"] == "final":
            return decision["answer"]

        if decision["type"] != "tool_call":
            return "模型返回了无法识别的动作"

        validate_tool_call(decision)
        result = execute_tool(
            decision["tool"],
            decision.get("arguments", {})
        )
        state = update_state(state, decision, result)
        save_state(state)
        context = build_context(user_goal, state)

    return "任务达到最大执行步数，未能完成"
```

生产系统还应补充超时、重试、幂等、并发控制、日志脱敏、权限检查和人工接管机制。

## 7. Agent、RAG、工作流和多智能体

这些概念可以组合使用，但关注点不同：

| 概念 | 核心作用 | 典型特征 |
|---|---|---|
| Agent | 围绕目标自主决策并执行 | 下一步可由结果动态决定 |
| RAG | 检索外部知识提供给模型 | 重点是检索和引用相关内容 |
| Workflow | 按预先设计的步骤执行 | 稳定、可控、易测试 |
| Multi-Agent | 多个 Agent 分工协作 | 不同角色负责不同子任务 |

例如论文调研系统：只搜索并总结是 RAG；固定执行“搜索—筛选—总结”是工作流；能根据搜索结果换关键词、继续验证结论的是 Agent；由检索 Agent、分析 Agent 和审查 Agent 协作则是多智能体系统。

## 8. 错误处理与可靠性

Agent 的错误不仅来自模型，也来自工具和环境。建议至少处理以下情况：

- 模型输出格式错误：要求结构化输出并进行 schema 校验；
- 工具参数错误：执行前校验类型、范围和必填字段；
- 工具运行失败：区分可重试错误和不可重试错误；
- 超时：设置单次工具超时和总任务超时；
- 重复执行：为写操作设计幂等键或状态检查；
- 上下文过长：摘要历史并只检索相关记忆；
- 结果不可信：增加校验工具、交叉验证或审查步骤；
- 无限循环：限制最大步数、重复动作次数和预算。

可靠性评估不能只看最终回答，还应关注任务完成率、工具调用成功率、平均步骤数、重试率、成本、延迟和人工接管率。

## 9. 安全设计

Agent 具备行动能力后，安全边界是系统设计的一部分：

1. **最小权限**：每个工具只获得完成任务所需的权限；
2. **输入校验**：不要直接信任模型生成的路径、SQL 或命令；
3. **沙箱执行**：对代码执行、文件操作和网络访问设置隔离环境；
4. **敏感信息保护**：避免把密钥、个人信息和内部提示词泄露给模型或日志；
5. **人工确认**：对不可逆或外部可见操作设置确认节点；
6. **审计追踪**：记录模型决定、工具参数、执行结果和最终状态；
7. **提示词注入防护**：把外部文档当作不可信数据，不能让其覆盖系统规则。

## 10. 开发建议

建议按以下顺序迭代：

1. 实现基本的模型对话；
2. 添加一个只读工具，例如读取文件或查询数据；
3. 增加结构化工具调用；
4. 实现执行循环和最大步数限制；
5. 加入状态保存和错误处理；
6. 加入相关记忆检索；
7. 增加日志、评估和权限控制；
8. 最后再根据实际需要引入多智能体。

不要一开始就把所有能力放入一个 Agent。工具数量过多、权限过大、上下文过长都会降低可控性。优先选择边界清晰、可观测、容易验证的工具。

## 11. 总结

Agent 不是一种新的大模型，而是一种围绕大模型构建的系统形态。它把模型的理解和决策能力，与工具、记忆、规划、执行器、状态管理和安全控制连接起来，形成一个能够持续行动的闭环。

理解 Agent 时，可以重点掌握以下关系：

- LLM 负责理解、推理和决策；
- Planning 负责拆解目标并安排步骤；
- Tools 负责与真实环境交互；
- Executor 负责安全、确定地执行动作；
- Memory 负责保存和检索有用上下文；
- Feedback Loop 负责根据结果继续行动；
- Runtime Control 负责限制风险、成本和执行范围。

对于大多数项目，“一个模型 + 少量工具 + 清晰的执行循环 + 可追踪状态”已经足以构成一个实用 Agent。复杂的规划、多智能体协作和长期记忆，应当在明确的业务需求出现后再逐步引入。
